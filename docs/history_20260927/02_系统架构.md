# 02 · 系统架构

## 1. 总览
```
患者端（手机网页 /p）          医生端（桌面网页 /d，含 /d/e/:id/print 打印版）
      │  REST /api/patient            │  REST /api/doctor
      ▼                               ▼
┌──────────────────────── FastAPI 后端 ────────────────────────┐
│ services/encounter.py   流程编排（就诊前 / 随访 / 医生操作 / 埋点）  │
│ facts/store.py          事实状态库（六状态、证据、版本、矛盾、核对）  │
│ questioning/engine.py   问询引擎（紧急终止 → 澄清 → 一键核对 → 协议题）│
│ extraction/service.py   抽取服务（模型候选 → 程序校验 → 写入）       │
│ summary/build.py        摘要（只由事实生成；叙述可由模型改写）        │
│ summary/brief.py        紧急程度、接诊速览、病历初稿（确定性整理）    │
│ verification/checks.py  验收（九项约束检查；浏览只计算、变更才落库）   │
│ tasks/service.py        任务 / 通知 / 审计（人推进）                 │
│ protocol/               协议 schema + YAML 加载 + 安全表达式         │
│ llm/provider.py         模型适配：mock / anthropic / compat + 兜底   │
└───────────────┬──────────────────────────────┬───────────────┘
                │ SQLite（原型）/ Postgres        │ protocols/*.yaml（医生维护）
```

## 2. 数据流：一次就诊前采集
1. `POST /api/patient/encounters` → 创建 Encounter，按协议初始化所有事实为 `not_asked`。
2. `POST .../body-map` → 存 Entry(body_map)；确定性推导部位、侧别、放射区域；**不标放射 ≠ 否认放射**。
3. `POST .../text` → 存 Entry(free_text)；模型抽取候选 → 校验（key 存在、quote 逐字在原文、值合法）→ `set_fact`（可能进入 conflicting）→ 评估红旗（紧急级立即向患者展示经审核的提示并生成任务）。
4. `GET .../next-question` → 引擎按四段顺序出题（见 §4）；返回 `stop_reason`，紧急终止时患者端跳到"请现在就联系医生"页。
5. `POST .../answer` → 存 Entry(answer)；写事实 / 标 `asked_unanswered` / 处理一键核对；评估红旗；返回下一题与终止信息。
6. `POST .../confirm` → 应用修改；矛盾未清则拒绝（**紧急终止时例外**：带着矛盾交给医生）；生成摘要 v1；创建"待医生核对"任务；跑验收并落库。
7. 医生 `GET /api/doctor/encounters/:id?actor=` → 状态 under_review；返回摘要（患者未确认但已有红旗时给一份**临时整理**，不落库）、事实+证据、原始记录、任务、验收（只计算不落库）、终止信息。
8. 医生修正 → 新版本 + 审计；确认 → 门槛检查；设置随访计划 → 通知 queued→sent + 随访任务。

## 3. 模型的边界（硬约束）
| 模型可以 | 模型不可以 |
|---|---|
| 从口语抽取协议定义的事实，附逐字引用 | 决定问什么、问多少、何时终止 |
| 把已整理的事实行写成 2–3 句叙述 | 触发红旗、改事实状态、跳过核对 |
| — | 给诊断、病名、药名、剂量、检查或训练建议 |

所有模型输出都经过程序校验：引用不在原文 → 丢弃；key 不在协议 → 丢弃；取值不合法 → 丢弃；叙述命中越界正则 → 验收失败。叙述**不携带**患者自由文本与药名（用药自述只在事实表里带出处展示）。

### 3.1 三种提供者（`TIJI_LLM_PROVIDER`）
| 提供者 | 用途 | 实现要点 |
|---|---|---|
| `mock` | 离线基线、演示兜底、测试 | 协议词表关键词匹配；短句切分；"好像/可能/说不清"才算不确定，"有点"是程度 |
| `anthropic` | 真实模型评测与决赛演示 | 官方 SDK `beta.messages.parse` + Pydantic 结构化输出；默认 `claude-opus-5`；`fallbacks="default"`（服务端拒答回退）；system 提示 `cache_control`；`output_config.effort` 抽取 medium、叙述 low；拒答与接口错误转为 ProviderError |
| `compat` | 国产模型（DeepSeek / 通义千问 / 智谱等 OpenAI 兼容接口） | JSON 模式 + 同一 Pydantic 模型校验，不合法时带错误信息重试一次 |
真实模型失败时 `TIJI_LLM_FALLBACK=mock` 自动退回离线词表，抽取结果与摘要标注 `mock(fallback)`；医生端顶栏显示当前模型。评测脚本强制 `none`，失败如实暴露。
兜底接住**任何异常**，不只 ProviderError（第二轮评审实测：没有 key 时 SDK 抛 TypeError，旧版患者端直接 500）；模型构建失败（缺配置）时用"未就绪"占位并同样退回。最近一次错误、未就绪原因、调用与失败次数都在 `/api/health` 的 `llm` 里，医生端顶栏标黄。连通性自检：`make llm-check`（命令行）或医生端顶栏"模型自检"（`POST /api/llm/probe`，30 秒内重复调用返回上次结果），用一句固定测试原话跑一次真实抽取，不放进每次健康检查。
医生端提效（第二轮评审后，按"AI 定位先看谁、该问什么，不定位什么病"）：
- 紧急程度 `triage_of`：只看已触发的协议红旗，患者核对时否认的紧急红旗按"当天联系"；`GET /api/doctor/encounters` 按紧急程度、再按是否等医生核对排序。
- 接诊速览 `visit_brief`：紧急程度、一句话主诉、红旗、面诊要当面确认的前三项（矛盾 > 关键事实表达不确定 > 关键事实未明确 > 必填未明确 > 其它不确定），随 `doctor_view` 返回。
- 病历初稿 `record_draft`：只用事实库拼主诉 / 现病史 / 阴性 / 表达不确定 / 未明确 / 患者原话 / 红旗 / 适用范围；用协议事实的 `record_label`（病历用短标签）；药名只出现在患者原话的「」里。不调用模型。
- 给患者的说明 `POST /api/doctor/encounters/{id}/followup-draft`：医生写要点，`provider.patient_explain` 只改写措辞（离线模式只分条、不改字）；改写里出现要点里没有的药名、病名、剂量，或要点里写了时间而随访间隔没填，都返回提醒；复诊时间与紧急提示由系统拼接；不自动发送，医生核对后用 followup-plan 发送并记下 `drafted_with`。
每段自由描述的抽取过程写审计日志 `extraction.completed`（用了哪个模型、写入 / 丢弃几条、协议外提到了什么），医生端原始记录里逐条可见。
**合规提示**：境内面向公众的生成式 AI 服务需按《生成式人工智能服务管理暂行办法》履行备案等义务；真实患者数据应使用已备案的境内模型或私有化部署。Claude 仅用于原型评测与演示（模拟数据）。

## 4. 问询引擎（questioning/engine.py）
按顺序取第一个满足的：
0. **紧急终止**：存在生效中的 `on_trigger: stop_questioning` 红旗（协议里紧急级）→ 若触发它的事实只来自文字抽取且未核对，先出一道"紧急核对"（防止误抽导致误报）；否则**不再出题**。
1. **矛盾澄清**：任一事实为 conflicting → 澄清题（协议模板或通用模板）。
2. **一键核对**：只从自由文本抽取、未经患者直接回答的关键事实（critical 或红旗类）→ 一道多条目核对题，每条选"对 / 不对 / 不确定"。
   - 对 → 追加一条患者确认证据；不对 → 事实回到"未询问"，由协议题重新直接问；不确定 → 记为不确定，协议题也会再问。
   - 触发红旗的整理被否定且条件不再成立 → 红旗标记"患者否认"（红旗与任务保留给医生电话确认），不再终止问询；之后若直接回答又确认 → 重新生效。
3. **协议问题**：按 `(tier, priority)`；已明确 / 已问过 / 条件不满足的跳过；达到 `max_questions` 后只问 tier 1（必问）；核对题与 tier 1 题不计入题数。

设计意图：**漏抽由问卷兜住，错抽由核对兜住，紧急情况不让患者继续答题。**

## 5. 状态机
### Encounter
`draft → questioning → awaiting_patient_confirmation → ready_for_doctor → under_review → doctor_confirmed → closed`
- 患者输入只在前三个状态允许；`ready_for_doctor` 之后患者端只读。
- 紧急终止时直接进入 `awaiting_patient_confirmation`，患者可"把已填写的内容交给医生"。
- `follow_up` 只能关联 `doctor_confirmed/closed` 的父就诊，且患者一致。

### Fact（单个事实）
| 当前 \ 新证据 | present/denied（同值） | present/denied（异值或相反） | uncertain | 修正（is_correction） |
|---|---|---|---|---|
| not_asked / asked_unanswered | 采纳 | 采纳 | 采纳 | 采纳 |
| uncertain | 采纳（升级为明确） | 采纳 | 合并证据 | 采纳 |
| present / denied | 合并证据 | **conflicting**（保留双方候选） | 不降级，合并证据 | 覆盖，旧版保留 |
| conflicting | 追加候选 | 追加候选 | 追加候选 | 覆盖（澄清结果） |
另有两个核对专用操作：`attach_evidence`（值不变，只加证据）、`reject_extracted_fact`（回到未询问，新版本不携带被否定的抽取证据，旧版本留在版本链）。

### Alert
触发 → （紧急级）立即提示 + 任务 → 患者核对否认且条件不再成立：`patient_disputed=true`（提示保留、任务加注"请电话确认"、不再终止问询）→ 直接回答再次确认：重新生效。

### Task / Notification
Task：`unviewed → viewed → {contacted | pending | escalated} → completed`，completed 必须由人。
Notification：`queued → sent | failed`；`sent → seen → acknowledged`，后两步只能由患者端写入。

## 6. 验收检查（verification/checks.py）
| id | 检查 | 严重度 |
|---|---|---|
| V1_provenance | 每条事实都有存在的原始记录作证据 | critical |
| V2_no_autocomplete | 未知事实无值；"明确否认"只含 denied；关键未知列入缺口 | critical |
| V3_quote_integrity | 文字证据逐字在原文中 | critical |
| V4_scope_guard | 系统生成文字（叙述、澄清题、核对题、系统通知）不含诊断/处方/剂量；患者原话（text 类与用药类事实的值）命中这类内容或疑似指令时，摘要里必须带"患者原话，不是系统建议"标记（`verification/scope.py`） | critical |
| V5_conflict_surfaced | 矛盾必须呈现 | major |
| V6_red_flag_handling | 红旗有提示、有任务、完成需人工 | critical |
| V7_notification_state | 通知流转合法；看到/确认由患者端记录 | major |
| V8_version_integrity | 摘要/事实版本链完整，系统版保留 | major |
| V9_confirmation_gate | 患者确认在前；医生确认时无矛盾 | critical |
医生端浏览时 `run_checks(persist=False)` 只计算；患者确认、医生修正/编辑/确认时才落库，"最新报告"语义稳定。

## 7. 可用性测试埋点
`POST /api/patient/encounters/:id/events`，白名单事件（page_view、step_submit、answer、verification、confirm_edit、confirm_submit、urgent_screen、urgent_action 等），payload 只保留标量，**不记录输入内容**。`eval/user_test/summarize.py` 汇总患者编号以 `UT-` 开头的记录。

## 8. 部署与切换
- 数据库：`TIJI_DATABASE_URL`，SQLite 原型；Postgres 改 URL 即可。新增列由 `db._ensure_columns()` 自动补齐（原型用，正式环境换迁移工具）。
- 模型：见 §3.1 与 `backend/.env.example`。
- 演示接口 `/api/dev/*`（seed、followup-parent）由 `TIJI_ENABLE_DEV` 控制，生产关闭。
- 通知通道：`tasks/service.py::deliver_queued` 是演示通道；接短信/公众号时替换，失败要标 `failed`。

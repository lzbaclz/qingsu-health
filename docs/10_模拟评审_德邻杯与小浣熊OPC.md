## 4. 详细意见

### 4.1 产品与工程：强项
1. **原则落到代码里，而不是停在 PPT**：六种事实状态（`FactStatus`）、不可变 Entry、证据 quote 逐字校验（V3）、版本链（`superseded_by`）、任务完成必须有人（`transition_task` 拒绝 system）、通知 seen/acknowledged 只能患者端写。这是评委在其它"AI 问诊"项目里看不到的东西。
2. **模型边界清晰**：`LLMProvider` 只有 `extract` / `narrative` 两个方法；问什么、何时升级、给患者看什么全在 YAML；换国产模型只需实现接口——这直接回答了"模型换了怎么办"。
3. **可复现的评测与诚实的变更记录**：`make eval` 9 秒跑完 80 场景；CHANGELOG 主动承认锁定集在调试中被看过。评委若懂评测，这是信任加分。
4. **前端质量高于原型平均水平**：患者端四步导航、进度条、全程紧急横幅、澄清题文案；医生端摘要 / 身体图 / 缺口 / 矛盾 / 红旗 / 事实表 / 验收 / 任务 / 原始记录一屏可达；随访变化卡 changed / new / unconfirmed 清晰。构建无类型错误。
5. **AI 模拟医生工作表**（NICE NG59、GIRFT CES 2023、Lancet 2018、中国 2024/2022 指南等 15 条来源，带 ⚠ 存疑标记，且提示 STarT Back 版权）是一份高质量的"给医生的起点"，本身就能作为"我们如何与临床协作"的展示物。

### 4.2 "AI"与评测的可信度：最大的技术短板
1. **默认演示模式没有模型**。`TIJI_LLM_PROVIDER=mock` 用协议词表做关键词匹配；评测 1.0 是"作者写的词表 × 作者写的场景"，是回归测试，不是能力证据。BP 里若只写"关键事实完整率 1.0"，懂行的评委会当场质疑。
2. **脱离词表的口语会漏、会错**（附录 A 实测 4 句）：
   - "尿有点费劲" 未抽到 `bladder_bowel_change`（红旗漏抽）；
   - "昨天差点摔了" 被记为 `trauma_recent = 是`（编造，E2）；
   - "腰疼老毛病了" 把 `onset_timing` 记成"超过 3 个月"（理解错，E8；协议 notes 自己预警过）；
   - "两条腿都软，走路像踩棉花" 未抽到 `leg_weakness`。
   关键的设计后果：**漏抽会被后续问卷兜住**（未知事实会被问），但**错抽不会**——事实一旦为 present，引擎就不再问该题，错误一路带进摘要（只剩确认页靠患者自己发现）。
3. **真实模型路径没有任何评测数据**。`AnthropicProvider` 用 `messages.parse` 结构化输出（本机 SDK 1.8.0 支持），代码看起来可用，但没跑过 eval，也没有与 mock 的对比报告。评委问"换成真模型是多少"，现在答不出。
4. **80 个场景实为 20 个病例家族 × 4 种改写**，全部工程自写、未经临床审核；锁定集已被调试污染（文档承认）。对外只能称"开发基线"。
5. mock 模式的叙述是模板拼接（"患者报告：这次不舒服开始多久了 6 到 12 周；起病方式 慢慢出现；……"），医生端读起来生硬；真实模型下会好很多——又一个决赛必须开真模型的理由。

### 4.3 临床与协议
1. **协议全部"待填写 / 待审"**：owners 两栏空、review.sources 空、`clinical_review_required` 全 true、场景 `review` 全 null。对医疗项目，这等于"临床这条腿还没落地"。
2. **红旗触发后仍继续问 16 题**：`rf_bladder_bowel` 为 urgent，但 `on_trigger: continue`。临床评委会问：告诉患者"立即去急诊"之后，为什么还让他答 15 道题？建议 urgent 级改为 `stop_questioning`（或只补问剩余 tier 1 题），把"去急诊 / 联系门诊"做成主按钮。
3. **缺范围核查事实**：S013（孕 28 周）系统无法识别不适用；v0.2 AI 草案已加入 age_band、pregnancy_status，应在医生审核后至少采纳这两项。
4. **CES 相关问法未限定"新发 / 两周内"**；AI 草案的建议（任何新报告 CES 症状一律急诊、医生事后降级）需要医生拍板并写进 patient_message。
5. 对比表（AI 版 vs 医生版）是很好的评审素材：**分歧行**最能证明"医生真的在做临床产品负责人"。现在医生栏全空。

### 4.4 需求、商业与竞争
1. **零一手证据**：没有访谈、没有意向书、没有"现在谁整理、花多久、漏过什么"的任何数字或引语。这是德邻第一把尺子，也是 BP 第 2 页，目前为空。
2. **定价是假设**（1,000/2,000/3,000 元/月），没有支付意愿数据；没有自下而上的市场估算（例如一个城市有多少康复 / 疼痛 / 全科门诊、每家月接诊量、可触达的首批 10 家从哪来）。
3. **竞品页只是名单**。需要一张三轴表：面向机构 vs 面向大众；协议驱动、可回溯 vs 自由问答；责任链 / 任务 vs 只给信息。先把主张说出来，再标"待验证"。
4. **预算 4.8 万**与 200 万 / 500 万级赛事不匹配。诚实是好事，但要补一页"若进入 Residency 获投的 12 个月计划"：多专科协议库、2 位临床、10 家试点、合规咨询——评委投的是"细分龙头"的路径，不是 90 天的省钱方案。

### 4.5 团队与合规
1. **团队页是最薄的一页**。需要：医生的姓名、职称、科室、每周投入、股权 / 署名安排（docs/08 §8 已列，但要落地成文字）；第二位独立复核者；谁负责销售与机构关系。路演人必须是创始人；Residency 是深圳 10 周——要明确表态能否投入。
2. **部署安全**：无登录 / 权限、无 TLS、`/api/dev/seed` 默认开启、医生身份是浏览器里一段文字、任何知道就诊 id 的人都能读患者数据。原型阶段可以接受，但 BP 第 7 页要给一张带日期的清单，不能只写"待做"。
3. docs/06 的合规框架（不诊断不处方、医嘱医生亲写、假名化、真实患者前的门槛）写得比多数医疗项目好，保留；补一句"数据控制者是门诊，我们是受托处理方，支持私有化 / 本地模型"。

### 4.6 演示与 BP 表达
1. 一句话定位太抽象。"面向专科门诊的 AI 症状表达与病程协作工具" 不如："**帮小型专科门诊把患者在见医生前、和两次就诊之间说的话，变成可核对的信息和有人负责的事项。**"
2. 开场用一个真实门诊故事（来自访谈），不用原则清单开场；七条原则放到第 3 页一张图里。
3. 决赛演示的三条路径已经很好，但每条要有一句"评委带走的话"：路径一 "没答的题会以未知进摘要，不会变成没有"；路径二 "我们不替患者选"；路径三 "系统只能创建任务，已完成必须有人"。
4. 证据页每项打四类标签，并把**真实模型 + 压力集**的数字加进去，否则"1.0"会引来反问。

### 4.7 代码层面的小问题（不影响比赛，顺手记）
- `doctor_view` 每次 GET 都执行 `run_checks` 并落一行 `VerificationReport`：刷新一次多一行，"最新报告"语义会漂，数据库随浏览增长。建议只在状态变化时跑，GET 读最近一份。
- `_next_seq` 每次全表数 Entry；`get_or_create_patient` 用 count 生成编号，有并发重复风险。原型可忽略。
- `answer_question` 的 `_interpret_answer` 对 bool 只认 "no/false/0/否/没有"，其它一律为 present；前端固定传 yes/no，没问题，但 API 直接调用时 "不清楚" 之类字符串会被当作"有"。
- 事实表 28 条里，随访专用事实在 pre_visit 已正确隐藏；但"未询问"的 text 类事实（prior_treatment 等）排在表首，医生第一眼看到的是三行"未询问"，建议按 key_facts_order 或把未问项默认折叠（前端已有"隐藏未询问"开关，默认可打开）。
